# 源码分析文档内容标准

> 软件：bookwright — 源码分析成书工具 v0.1
> 版本：v0.1
> 定位：**内容标准**——一本"读源码 → 出文档"的书，内容上必须满足什么。与语言、
> 仓库、书名都无关，换一份源码树照样适用。本文只回答"必须有什么"，不回答"怎么写"，
> 也不声明判据与级别。

## 1. 两轴分工

| 轴 | 回答的问题 | 归谁 |
| --- | --- | --- |
| 内容要求 | 这一章必须有什么 | 本文 |
| 写作方式 | 这些内容怎么写成文字（句式、排版、图注措辞、练习格式） | `../manuals/how-to-write.md` |

判据、级别与门禁**不属于本标准**：那是采用它的项目自己的事，登记在该项目的质量计划里。
引用方向只有一个——项目指向本文（"这道门禁判的是本标准哪一节"），本文不反向引用任何
项目的门禁表、脚本或配置文件。这样本文才能换一份源码树、换一个工具链继续适用。

## 2. 适用对象与目标

- **读者**：需要在不读完全部源码的前提下，判断"改哪里、会影响谁"的工程师。
- **目标**：让每个结论都能回到源码坐标，让每一章都能独立阅读。
- **非目标**：API 手册、教程式入门、架构评审结论；这些由别的文档承担。

## 3. 四层信息阶梯（每章都必须齐备）

| 层次 | 回答的问题 | 必备内容 |
| --- | --- | --- |
| 版图 | 这一块有哪些组成？ | 包/模块表：位置、规模、职责一句话 |
| 类型 | 谁在承担职责？ | 核心类型表：职责、规模、公开面 |
| 入口 | 从哪里进入、往哪去？ | 关键 API ↔ 源码坐标（`file:line`） |
| 路径 | 该按什么顺序读？ | 阅读顺序 + 跨章衔接点 |

四层缺一层即视为不合格。表格过长时用"其余见附录"收敛；具体行数预算由项目配置给出。

## 4. 事实要求

1. 每个源码引用必须可解析：`org/.../File.java:行号` 或 `Class.method(`。
2. 引用的行号必须落在文件长度内；方法必须存在于该类。
3. 包级结论必须来自 `package-info` 或类注释；无注释时须标注为归纳。
4. 上游更新后，引用与坐标必须重新生成，不接受"人工记忆"的修正。

这四条都可枚举，因而都可以由项目写成检查：坐标与符号的可解析性、摘录与源码的一致性。

## 5. 章节骨架

```text
# 第N章 标题
> 本章导读（范围 / 读完能做到什么 / 前置知识）
> 术语参考（指向术语表）
N.1 版图    N.2 核心类型    N.3 入口与坐标    N.4 阅读路径
N.5 依赖方向（可选）   N.6 设计权衡   N.7 常见误区
N.x 本章小结   N.y 延伸思考   N.z 延展阅读
```

骨架中被强制的那部分（哪些段落必须存在、叫什么名字、什么顺序）由项目配置给出；
引导块与章末段落的具体写法见 `../manuals/how-to-write.md` §7。

## 6. 图示与表格

- 图必须有独立成行的图注；图注说清"展示了什么关系"，而不是复述图里已有的字。
- ASCII 图宽度受列数预算约束（中日韩字符按 2 列计）；宽度上限由项目配置给出。
- 表格优先于长段落；表格首列是被描述对象，末列是判断依据或坐标。

图注句式、动词表与长度区间的写法见 `../manuals/how-to-write.md` §14。

## 7. 术语与引用

- 术语首次出现应能在术语表命中；术语表条目需标明章节与相关术语。
- 同义词择一并用到底（如"页/page""快照/snapshot"不混用）。
- 章间互引必须真实存在，且指向真实的章节标题。

跨章引用的句式与标题一致要求见 `../manuals/how-to-write.md` §5。

## 8. 练习与可迁移性

每章必须有延伸思考，题目要求"回到源码找证据"而不是复述结论；题型、难度标度、题量、
提示行与回顾行怎么写，全在 `../manuals/how-to-write.md` §12，本文只要求它存在且可回答。

## 9. 内容自查（人工项）

以下四问无法靠形式检查回答，定稿前逐条回答"是/否"：

| # | 自查项 | 判断 |
| --- | --- | --- |
| 1 | 读者能否只读本章就动手 | 结论、坐标、阅读顺序自足 |
| 2 | 论述是否被代码证明 | 关键判断都有可核对的坐标，而不是经验之谈 |
| 3 | 一章是否只有一个主线 | 副线让位或另立一节，不并列铺开 |
| 4 | 练习是否考到本章主线 | 题目指向本章类型或小节，而不是通用常识 |

可枚举的部分（结构、编号、链接、术语、体量）不在此列，由项目自己的检查承担。

## 10. 与采用它的项目的关系

本文只定义内容标准。项目在自己的质量计划里登记"哪道门禁判定本文哪一节、判到什么级别"，
并自行决定实现方式；本文既不指定门禁，也不规定阈值。

项目侧另有三件事：交付什么、判据与级别、谁判与代价多少。它们由项目自己的文档承担，本文不
指名也不依赖其结构。两者的关系只有一条：**内容是本文定义的，判定是项目注册的**——标题层级、
四种信息阶梯这类"必须有什么"以本文为准，门禁、阈值与基线以项目为准。

新增一条标准时补两处：本文一节（要求），项目一行（判定）。缺任何一处，标准就只停留在纸面。
