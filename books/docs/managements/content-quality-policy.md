# 内容质量方针

> 软件：bookwright — 源码分析成书工具 v0.1
> 版本：v0.1
> 定位：**成书内容的方针**——内容质量由谁判、什么时候判、基线怎么记、代价多少。它不管"内容必须有什么"
> （那是 `content-standard.md`），也不管"某道门禁判什么、几级、怎么跑"（那是 `testplan.md`），
> 实现与约束在 `technical.md`；本文回答的是"这套分工为什么成立、一份内容凭什么算过了"。

## 1. 三层分工

| 层 | 载体 | 负责 | 不负责 |
| --- | --- | --- | --- |
| 风格文件 | `data/config/style.json`、`data/config/base.json`、`data/book/book.toml`、`data/language/` | 阈值、词表、章节顺序、语言映射；唯一的政策事实来源（`../manuals/how-to-write.md` 只解释规则怎么读，不持有取值） | 判断某段文字是否真的说清楚了 |
| 脚本门禁 | `src/python/audit/*`、`src/python/render/verify_*` | 一切可枚举、可复现、可基线的判定：体量与结构、编号与链接、术语一致性、图注形态、代码摘录与源码一致 | 语义正确性、叙述是否成立 |
| LLM | `lib/_llm.py`（`app/` 与 ingest 散文场景） | 生成初稿、评审语义、给出改写建议；产出**建议**，不产出结论 | 任何门禁判定、任何数字、任何「通过/不通过」 |

判定顺序固定：脚本先给出可复现的失败集合，LLM 只在集合之内工作；LLM 的产出必须
再次经过脚本（或人工复核）才能进入手稿。`audit/llm_policy.py` 用结构检查保证这条
边界不被越过——门禁层不得导入 `lib._llm`。

## 2. 三种起点

同一套工具链，三种起点。起点由 `base.json [toolchain] content_profile` 声明，
门禁按它决定「体量与质量各自保护什么」。

| | A 增量（有历史稿 + 代码有变更） | B 返工（历史稿水平不足） | C 冷启动（无历史稿） |
| --- | --- | --- | --- |
| `content_profile` | `baseline` | `rewrite` | `cold-start` |
| 主导者 | 脚本 | 脚本判形态，LLM 改写 | LLM |
| 第一道门禁 | `source_refs.py`：上游改名/删方法必须先对齐 | `content_volume.py`：改写不得连带删内容 | 结构门禁：章节清单与标题层级先立 |
| 体积门禁 | 严格，逐章 95% 下限 | 严格；某章确实要缩，须评审后 `--update-baseline` | 仅提示（无存量可保护） |
| 质量门禁 | 存量入基线，新增即红 | 基线只收“尚未改写”的章节，改完一章重设一章 | 全量按门禁判，无基线 |
| LLM 的位置 | 只写变更涉及的章节、桥接句、图注改写 | 逐章重写，脚本校验措辞形态与锚点 | 切分章节、归纳主线、术语初选、写初稿 |
| 完成判据 | 全部门禁绿 + 交付产物完整 | 每章重写后体积不低于原文、质量警告归零 | 结构门禁全绿，然后固化首版基线转 A |

代码是否变更不由人判断：`data/state/source-inventory.json` 记录被分析源码的快照，
`source_refs.py` 负责把书里的 `Class.method` 断言对到新源码上；上游升级后先跑它，
拿到改名/缺失清单，再决定改哪几章。

三种起点在工具链上只有一处分支（体积门禁的严格度），其余判定完全相同——这正是
「脚本做多数工作、LLM 做加分」可落地的前提：判据不随起点变，只有保护对象变。

## 3. 判定归属

| 判定 | 归属 | 理由 |
| --- | --- | --- |
| 章节齐全、标题层级连续、图号唯一 | 脚本 | 可枚举 |
| 内容体量不低于基线、交付页数不缩水 | 脚本 | 可比较，`content-volume` 门禁 |
| 链接与锚点、索引与术语表引用 | 脚本 | 可解析 |
| 图注形态（动宾起首、长度、桥接句） | 脚本判定形态，LLM 改写文案 | 形态可枚举，措辞需生成 |
| 「这段结论是否被代码证明」 | LLM 建议，脚本校验符号与行号 | 语义判断 + 事实可核对 |
| 「这一章的叙事主线是否成立」 | LLM | 无形式判据 |
| 「与前文是否重复」 | 脚本算相似度，LLM 判取舍 | 相似度可算，取舍需判断 |
| 代码摘录与源码一致 | 脚本 | 逐字比对 |
| 练习题是否考到本章主线 | LLM 生成，脚本校验锚点与计数 | 生成 + 可枚举 |
| 版式是否可读（每行 `em` 落在阅读区间、栏宽不超可印宽度） | 脚本 | 由阅读度量与纸张推导，与书、字体无关 |
| 交付耗时是否回退 | 脚本（advisory） | 与评审基线比，超阈值只提示，不阻塞 |
| 逐文件覆盖率是否低于棘轮 | 脚本 | 数字可复现，只升不降 |
| 源文件是否超出长度预算 | 脚本 | 行数可数，台账只报超阈值的增长 |

原则：能用枚举表达的，绝不用模型；模型给出的结论，必须能被某条脚本或人工核对复现。

## 4. 基线生命周期

1. 建立：定稿（或一次完整的人工评审）后 `--update-baseline`，写入 `data/baselines/`。
2. 收缩：条目已修复则下次运行报告「stale」，重新固化即收缩基线。
3. 新增：任何新出现的同类别问题直接判红，基线不能自动扩容。
4. 复核：基线文件是 JSON，逐条可读；接受一条等于接受一个已知缺陷，必须在评审中说明。

基线有三类，写入方式相同（评审 + 具名 + 提交），守护的东西不同：

| 基线 | 守护什么 | 新增问题 | 收缩方式 |
| --- | --- | --- | --- |
| 存量问题（`*-baseline.json`、`*-findings.json`、`loose-assertions.json`） | 已知且已评审的缺陷清单 | 同类问题一律失败 | 修复后报告 `stale`，重新固化 |
| 体量（`content-volume.json`、`snapshot-<标签>.json`） | 内容不得静默塌陷 | 低于下限即失败 | 见下文的单调性 |
| 测量（`perf-baseline.json`、`coverage.json`） | 耗时与覆盖率的可接受下限 | 超阈值只提示（advisory）或直接失败 | `--update-baseline` 重记 |

测量类基线只记「评审过的数」，读数本身进滚动窗口：`logs/perf-history.jsonl` 保留最近若干次
（`style.json [quality].perf_history_runs`），超过上限即原子重写保留最新段。窗口是样本，
基线是判据——清理样本不会移动判据。

体量基线（`content-volume.json`）多一条**单调性**：重记基线不允许把下限改低，
除非显式 `--accept-shrink --reason "<理由>"`，理由与逐项差额会写进基线文件
（`accepted_shrinks`）。否则「每转换一次就重记一次」会把下限一次一点地拉低，
某份写得好的旧稿就这样被悄悄替换成更薄的新稿，而且没有一处记录能看出来。

**「评审通过」是怎么被认定的。** 不是一句口头结论，而是三项可查的条件加一条记录：

1. **稿子已提交**：`data/manuscript` 没有未提交改动——基线必须指向一个提交，否则事后无法复原
   "当时评审的是哪一版"；
2. **不降低下限**：见上一条的单调性（要降就显式接受并写理由）；
3. **有具名评审人**：`--reviewed-by "<名字>"`（缺省取 `git user.name`），空白即拒绝记账。

满足后 `--update-baseline` 会在基线文件里写入 `reviewed` 段：
`{"by": "…", "at": "<提交时间>", "commit": "<短哈希>", "reason": "<为什么这版算定稿>"}`。
于是任何一次"这份稿子是不是基线"都能三句话回答：哪个人、在哪个提交上、凭什么理由。

流程（顺序固定，跳过任何一步都只得到快照而不是基线）：

```bash
make.py check                                   # 1. 全部门禁绿，说明这版值得记
git add -A books/data/manuscript && git commit  # 2. 稿子落到提交上
python books/src/python/audit/content_volume.py --update-baseline \
    --reviewed-by "阿龙" --reason "第 6 章补写完成，定稿"   # 3. 记账并留名
```

**把某一版历史稿提为基线**（例如认定 6 月那版更好）：历史稿是只读快照，不能直接量，
所以先导入、再记体积账本、最后提为基线，三步都有记录：

```bash
python books/src/python/manuscript/snapshot.py import ../docs-stm.zip june-2026 --date 2026-06-11
# 或直接取某天的归档目录（两者职责见 folder.md §3.1，无需先打包）：
# python books/src/python/manuscript/snapshot.py import data/archive/<书>/<日期>/manuscript <标签> --date <日期>
python books/src/python/manuscript/snapshot.py baseline 2026-06-11-june-2026
python books/src/python/audit/content_volume.py --update-baseline \
    --from-snapshot 2026-06-11-june-2026 --reviewed-by "阿龙" \
    --reason "该版结构与文风已定稿，作为下限" [--accept-shrink]
```

若该版比当前基线**薄**（换基线等于降低下限），必须显式 `--accept-shrink`，理由与逐项差额
一起入账——这是唯一允许降低基线的入口，一眼能查。提为基线后 `source.snapshot` 记下它来自
哪份快照，`reviewed` 记下谁在哪一提交上做的决定。

**比哪一份？只比一份。** 一次只有一条下限：当前 `content-volume.json` 里记的那份，
即最近一次经评审接受的稿子。不做加权、不做「组合概率」——基线是评审结论，不是统计量；
一旦变成平均值，就无法回答「这次转换有没有让稿子变薄」。
历史稿各自保留自己的体量账本（`data/snapshots/<日期>-<标签>/` 与
`data/baselines/snapshot-<标签>.json`）；要用某一份旧稿当参照，就显式指定：
`content_volume.py --baseline data/baselines/snapshot-2026-06-30.json`。
不指定时永远比当前基线。

基线只接住「已知且已评审的存量」，不接住结构缺项。章节数、章节体量、交付完整性
一律不进基线——它们代表文档本体，缺失就是内容事故。

## 5. 判据、实现与配置的归属

本文只定策略，具体位置各有权威，不再复制清单：

| 想知道 | 去哪看 |
| --- | --- |
| 一本书的内容必须有什么（与项目无关的标准） | 内容标准（`content-standard.md`） |
| 某道门禁的判据、级别、验证命令 | 质量计划（`testplan.md`） |
| 门禁的实现位置、依赖方向、可达性要求 | 技术设计（`technical.md`） |
| 阈值、词表、预算取值的文件与键 | 技术设计 §3.2「阈值归属」 |
| 已评审存量的清单与生成方式 | `data/baselines/`，路径映射在 `base.json [baselines]` |
| 耗时基线与滚动窗口的取值 | `data/baselines/perf-baseline.json`、`style.json [quality]` |
| 覆盖率棘轮与单文件下限 | `data/baselines/coverage.json`、`base.json [toolchain]` |

## 6. 反模式

- **静默基线化**：把新问题写进基线换取绿色。基线只收存量，新增必须红。
- **让 LLM 判门禁**：同一篇文稿两次运行结论可能不同，门禁必须确定。
- **用脚本猜语义**：正则匹配「是否正确」会制造假绿，语义判断交给人或 LLM。
- **只测单脚本**：每个脚本单独可用，不代表它被接入流程；`check_architecture.py`
  的 wiring 检查负责这一点。
- **用系统解释器跑交付**：依赖版本漂移会让同一命令在不同机器上产出不同结果，
  `.venv` 是唯一解释器，`make.py` 在入口处拒绝其它解释器。

## 7. 场景矩阵

起点（§2）只决定「保护什么」，场景决定「先跑哪几个门禁」。同一套工具链，按场景
选择入口，不新增规则。

| 场景 | 起点档 | 首个动作 | 关键门禁 | LLM 用在哪 |
| --- | --- | --- | --- | --- |
| A 上游升级、书要在旧稿上跟进 | `baseline` | `source_refs.py` 出改名/缺失清单 | 符号一致、体积、结构 | 只写变更涉及的章节 |
| B 旧稿在、深度不足 | `rewrite` | 逐章重写前先锁体积 | 体积、图注形态、风格 | 逐章改写正文 |
| C 全新项目分析 | `cold-start` | `book.toml` 定章节，`structure.py` 立骨架 | 结构、链接、编号 | 切分、主线、术语、初稿 |
| D 读者报错、局部返修 | `baseline` | `review_packet.py` 取上下文 | 全量（回归证明没连带破坏） | 只改被定位的那一段 |
| E 上游大版本重构、章节要重划 | `rewrite` | 先改 `book.toml`，再迁移内容 | 结构、体积（按新基线）、链接 | 章节归并与新主线 |
| F 多人供稿、文风不一 | `rewrite` | `style_rules.py` + `style.py` 先跑一遍 | 风格、术语、图注形态 | 统一措辞，不碰事实 |
| G 同一本书多语言 | `baseline` | 各语言章节数与图号必须一致 | 结构、图号、链接 | 翻译与本地化表达 |
| H 系列书、风格已定但要写新书 | `cold-start` | 复用风格文件，只建内容 | 结构、风格、体量 | 全量初稿 |
| I 代码没变、要把书写深 | `baseline` | `content_depth.py` 找前向引用与摘录陈旧项 | 深度、符号、体积 | 补论述与例题 |

场景之间可以迁移：C 定稿后转 A，E 迁移完成后转 A，D 永远是 A 的子集——所以
`content_profile` 只需在起点切换时改一次。

## 8. Token 经济

脚本负责覆盖面，LLM 负责判断与生成，这不是分工口号，而是成本结构：

| 做法 | 成本 | 说明 |
| --- | --- | --- |
| 通读全稿找问题 | 数 MB 文本 ≈ 数十万 token | 绝大部分内容早已通过门禁 |
| 跑全部门禁 | 秒级、零 token | `make.py check`，失败集合才是待办 |
| 只喂失败集合 | 通常 < 50 KB | `audit/review_packet.py` 输出失败项 + 每项 2 行上下文 |
| LLM 生成新章节 | 按新增内容计费 | 唯一值得付费的生成型工作 |

约定：

1. 任何「数一遍、比一次、对一下」的工作先问能不能脚本化，能就写门禁，不写 prompt。
2. LLM 的输入是 `review_packet` 之类的**失败集合**，不是整本书；输出的改写再被门禁
   复验一次，防止引入新的形态违规。
3. 已入基线的存量不进复核包，避免每次都重新讨论已评审过的旧账。
4. 门禁通过即停止讨论该维度——绿色维度不消耗 LLM 注意力。
